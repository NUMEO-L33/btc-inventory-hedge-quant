## 2. Authentication (인증)

상태: **VERIFIED** (HMAC / timestamp / recvWindow / RSA), **PARTIAL** (Ed25519 for REST)

- API key 헤더: "API-keys are passed into the Rest API via the `X-MBX-APIKEY` header."
- Security type 표: NONE "Endpoint can be accessed freely." / TRADE "Endpoint requires sending a valid API-Key and signature." / USER_DATA "Endpoint requires sending a valid API-Key and signature." / USER_STREAM "Endpoint requires sending a valid API-Key." / MARKET_DATA "Endpoint requires sending a valid API-Key." ; "TRADE and USER_DATA endpoints are SIGNED endpoints."
- 서명: "`SIGNED` endpoints require an additional parameter, `signature`, to be sent in the `query string` or `request body`. Endpoints use `HMAC SHA256` signatures. The `HMAC SHA256 signature` is a keyed `HMAC SHA256` operation. Use your `secretKey` as the key and `totalParams` as the value for the HMAC operation." / "`totalParams` is defined as the `query string` concatenated with the `request body`." / "Signature is the end part of query string or request body."
- 파라미터 전송: "For `GET` endpoints, parameters must be sent as a `query string`." / "For `POST`, `PUT`, and `DELETE` endpoints, the parameters may be sent as a `query string` or in the `request body`" (content type `application/x-www-form-urlencoded`)
- 공식 예제 (apiKey `dbefbc809e3e83c283a984c3a1459732ea7db1360ca80c5c2c8867408d28cc83`, secretKey `2b5eb11e18796d12d88f13dc27dbbd02c2cc51ff7059765ed9821957d82bb4d9`):
  - Example 1/2 totalParams: `symbol=BTCUSD_200925&side=BUY&type=LIMIT&quantity=1&price=9000&timeInForce=GTC&recvWindow=5000&timestamp=1591702613943` → signature `21fd819734bf0e5c68740eed892909414d693635c5f7fffab1313925ae13556a`
  - Example 3 (query string + request body 단순 연결, 구분자 없음): `symbol=BTCUSD_200925&side=BUY&type=LIMIT&timeInForce=GTCquantity=1&price=9000&recvWindow=5000&timestamp=1591702613943` → signature `f3129e7c72c7727037891ad8a86b76a7dc514ba125a536775c8ba403b2d1b222`
  - → ⚠️ 구현 검증 결과(2026-09-02): 위 COIN-M 예시의 서명값은 인쇄된 secretKey·문자열로 **재현되지 않음**(secret/메시지 조합을 바꿔도 불일치). 동일 방식의 USDⓈ-M General Info 예시(`symbol=BTCUSDT&side=BUY&type=LIMIT&quantity=1&price=9000&timeInForce=GTC&recvWindow=5000&timestamp=1591702613943` → `3c661234138461fcc7a7d8746c6558c9842d4e10870d2ecbedf7777cad694af9`)는 정확히 재현되므로 HMAC-SHA256(totalParams) 알고리즘 자체는 VERIFIED, COIN-M 예시값은 문서 오류로 판단(UNVERIFIED 예시). `tests/unit/test_binance_adapter.py` 참조.
- Timing: "A `SIGNED` endpoint also requires a parameter, `timestamp`, to be sent which should be the millisecond timestamp of when the request was created and sent." / "An additional parameter, `recvWindow`, may be sent to specify the number of milliseconds after `timestamp` the request is valid for. If `recvWindow` is not sent, **it defaults to 5000**." / 서버 로직: `if (timestamp < serverTime + 1000 && serverTime - timestamp <= recvWindow) { // process request } else { // reject request }` / "It is recommended to use a small recvWindow of 5000 or less!" ; 파라미터 스키마상 `recvWindow` "integer (int64, max: 60000)"
- 매칭엔진 측 재검사: Change Log 2023-04-17 "`recvWindow` check will also be performed when orders reach matching engine" ; 에러 `-4188 ME_INVALID_TIMESTAMP` "Timestamp for this request is outside of the ME recvWindow."
- RSA: "We support `PKCS#8` currently." / "To get your API key, you need to upload your RSA Public Key to your account" ; (USDⓈ-M 동일 페이지) "RSASSA-PKCS1-v1_5 algorithm with SHA-256 hash function."
- Ed25519: COIN-M REST General Info 페이지에는 Ed25519 언급 없음 (fetch 결과: "does not contain references to Ed25519"). WebSocket API 페이지: "Only *Ed25519* keys are supported for this feature." (WS API 세션 인증 맥락). [SDK] README: "You can use `RSA` or `ED25519` keys for signing requests." → REST Ed25519 지원은 **PARTIAL** (SDK 근거만 있음).

## 3. Rate limits

상태: **VERIFIED**

- "The `/dapi/v1/exchangeInfo` `rateLimits` array contains objects related to the exchange's `RAW_REQUEST`, `REQUEST_WEIGHT`, and `ORDER` rate limits." / "A `429` will be returned when either rate limit is violated."
- IP: "Every request will contain `X-MBX-USED-WEIGHT-(intervalNum)(intervalLetter)` in the response headers which has the current used weight for the IP." / "When a 429 is received, back off and not spam the API." / "Repeatedly violating rate limits and/or failing to back off results in automated IP ban (HTTP 418)." / "IP bans are tracked and **scale in duration** for repeat offenders, **from 2 minutes to 3 days**." / "The limits on the API are based on the IPs, not the API keys."
- Order: "Every order response will contain a `X-MBX-ORDER-COUNT-(intervalNum)(intervalLetter)` header which has the current order count for the account." / "Rejected/unsuccessful orders are not guaranteed to have X-MBX-ORDER-COUNT-** headers." / "The order rate limit is counted against each account."
- HTTP: "HTTP `429` return code is used when breaking a request rate limit." / "HTTP `418` return code is used when an IP has been auto-banned for continuing to send requests after receiving `429` codes." / "HTTP `5XX` return codes are used for internal errors; the issue is on Binance's side." / 403 "WAF Limit (Web Application Firewall) has been violated" / 408 timeout / 503 (unknown execution status / service unavailable / throttling)

### 실주문 코드 작성 시 반드시 지킬 것 (문서 근거 기반)
1. `POST /dapi/v1/order` 응답에는 `avgPrice`/`cumBase` 가 없다 → 체결가는 `GET /dapi/v1/order`·`userTrades`·`ORDER_TRADE_UPDATE(ap,L,l,z)` 로 확정.
2. `type` 은 LIMIT/MARKET 만 이 엔드포인트로; STOP 계열은 `-4120` (algoOrder API 필요, 세부 UNVERIFIED).
3. `quantity` 는 **계약 수(정수)**; 1 BTC 계약 = 100 USD; 필터(tickSize/stepSize/PERCENT_PRICE/MAX_NUM_ORDERS)는 런타임 exchangeInfo 로.
4. One-way 모드: `positionSide` 생략(=BOTH) + `reduceOnly` 사용 가능 ; Hedge 모드: `positionSide` 필수, `reduceOnly` 전송 금지.
5. `newClientOrderId` 는 `^[\.A-Z\:/a-z0-9_-]{1,36}$`.
6. `recvWindow` ≤ 5000 권장, 서버시간 동기화, -1021/-4188 재시도 로직.
7. listenKey: 30분마다 PUT, 24h 전 재연결, `listenKeyExpired` 시 즉시 재발급 ; `-1125` 처리.
8. 포지션 모드/STP/레이트리밋은 UM 과 공유됨(통합 이후) — USDⓈ-M 계정 설정과 충돌 주의.
9. 데모 환경 기본값: `https://demo-dapi.binance.com`, `wss://demo-dstream.binance.com` (접속 가능 여부 런타임 확인).

### 데모의 펀딩 요율 이력 부재 (신규 발견)

데모 환경은 **펀딩을 정산하면서도 그 요율 이력을 공개하지 않는다.** 정산 자체는 `income(FUNDING_FEE)` 로 확인되지만 `fundingRate` 는 항상 빈 배열이다. 공식 문서에 이 제약을 명시한 문장은 **없다(UNVERIFIED)**.

결과적으로 **데모만으로는 펀딩 공식(§6 PARTIAL)을 검증할 수 없다.** 요율과 마크가격 두 미지수에 방정식이 하나뿐이기 때문이다.

대응: `verify-funding --allow-production-rates` 로 공개 프로덕션 요율을 대입하되, 두 환경이 같은 가격을 매기는지를 `environments_agree()` 로 **측정해서 함께 보고**한다. 두 환경이 어긋나면 그 대입은 신뢰할 수 없으며 보고서에 그대로 표시된다. `premiumIndex.lastFundingRate` 는 **다음** 정산 예정 요율이라 대체 소스로 쓰지 않는다 — 거짓 VERIFIED 를 만들 수 있다.

## §18 데모 실측 (2026-09-27): `GET /dapi/v1/income` 은 `incomeType` 없이는 빈 배열

testnet 에이전트를 7일 무인 운영한 뒤 원장에 FUNDING_FEE 가 0건인 것을 발견했다. 같은 계좌, 같은
창(2026-09-20 이후)으로 직접 호출한 결과:

| 호출 | 결과 |
|---|---|
| 필터 없음 (대사 로직이 보내던 형태) | **0건** |
| `incomeType=FUNDING_FEE` | 22건, 합 0.00000237 BTC |
| `symbol` + `incomeType` + 시간창 | 22건 |
| `symbol` + `incomeType`, 시간창 없음 | 21건 (기본 창) |

데모는 정산을 했고 기록도 있는데, 필터 없는 조회에만 비어 있다. 공식 문서(§4)는 "If `incomeType`
is not sent, all kinds of flow will be returned" 이므로 **문서와 다른 데모 동작**이다. 프로덕션이
