## 3. Rate limits

Status: **VERIFIED**

- "The `/dapi/v1/exchangeInfo` `rateLimits` array contains objects related to the exchange's `RAW_REQUEST`, `REQUEST_WEIGHT`, and `ORDER` rate limits." / "A `429` will be returned when either rate limit is violated."
- IP: "Every request will contain `X-MBX-USED-WEIGHT-(intervalNum)(intervalLetter)` in the response headers which has the current used weight for the IP." / "When a 429 is received, back off and not spam the API." / "Repeatedly violating rate limits and/or failing to back off results in automated IP ban (HTTP 418)." / "IP bans are tracked and **scale in duration** for repeat offenders, **from 2 minutes to 3 days**." / "The limits on the API are based on the IPs, not the API keys."
- Order: "Every order response will contain a `X-MBX-ORDER-COUNT-(intervalNum)(intervalLetter)` header which has the current order count for the account." / "Rejected/unsuccessful orders are not guaranteed to have X-MBX-ORDER-COUNT-** headers." / "The order rate limit is counted against each account."
- HTTP: "HTTP `429` return code is used when breaking a request rate limit." / "HTTP `418` return code is used when an IP has been auto-banned for continuing to send requests after receiving `429` codes." / "HTTP `5XX` return codes are used for internal errors; the issue is on Binance's side." / 403 "WAF Limit (Web Application Firewall) has been violated" / 408 timeout / 503 (unknown execution status / service unavailable / throttling)

### Mandatory rules for writing live-order code (grounded in the documentation)
1. The `POST /dapi/v1/order` response has no `avgPrice`/`cumBase` → establish the fill price from `GET /dapi/v1/order`·`userTrades`·`ORDER_TRADE_UPDATE(ap,L,l,z)`.
2. Send only LIMIT/MARKET as `type` to this endpoint; STOP-type orders get `-4120` (algoOrder API required, details UNVERIFIED).
3. `quantity` is the **number of contracts (integer)**; 1 BTC contract = 100 USD; take the filters (tickSize/stepSize/PERCENT_PRICE/MAX_NUM_ORDERS) from exchangeInfo at runtime.
4. One-way mode: omit `positionSide` (=BOTH) + `reduceOnly` may be used ; Hedge mode: `positionSide` mandatory, never send `reduceOnly`.
5. `newClientOrderId` must match `^[\.A-Z\:/a-z0-9_-]{1,36}$`.
6. `recvWindow` ≤ 5000 recommended, server-time synchronization, -1021/-4188 retry logic.

### No funding rate history on the demo (new finding)

The demo environment **settles funding but does not publish the rate history.** The settlement itself is confirmed via `income(FUNDING_FEE)`, but `fundingRate` is always an empty array. The official documentation contains **no sentence stating this limitation (UNVERIFIED)**.

Consequently, **the funding formula (§6 PARTIAL) cannot be verified with the demo alone.** There are two unknowns, the rate and the mark price, but only one equation.

Mitigation: `verify-funding --allow-production-rates` substitutes the public production rates, but **measures and reports alongside it** whether the two environments assign the same prices, via `environments_agree()`. If the two environments diverge, the substitution cannot be trusted, and the report shows that as is. `premiumIndex.lastFundingRate` is the rate for the **next** scheduled settlement, so it is not used as a substitute source — it could produce a false VERIFIED.

## §18 Demo measured live (2026-09-27): `GET /dapi/v1/income` returns an empty array without `incomeType`

After 7 days of unattended operation of the testnet agent, the ledger was found to contain 0 FUNDING_FEE entries. Direct calls with the same
account and the same window (from 2026-09-20 onward) gave:

| Call | Result |
|---|---|
| No filter (the form the reconciliation logic used to send) | **0 entries** |
| `incomeType=FUNDING_FEE` | 22 entries, sum 0.00000237 BTC |
| `symbol` + `incomeType` + time window | 22 entries |
| `symbol` + `incomeType`, no time window | 21 entries (default window) |

Demo wallet 0.01000742 − ledger 0.01000517 = 0.00000225 = the sum of the 21 entries since the adoption point, **an exact match**. In other words,
the demo did settle and does have the records; only the unfiltered query comes back empty. The official documentation (§4) says "If `incomeType`
is not sent, all kinds of flow will be returned", so this is **demo behavior that differs from the documentation**. Whether production
follows the documentation could not be confirmed (UNVERIFIED). Mitigation: `Reconciler.sync_income` queries separately for each type
defined in the documentation — the result is the same under either behavior, and the cost is a few calls of weight 20 each, 1× per day.

Side note: the weekly funding of this account (0.01 BTC, 1 contract), 0.0000022 BTC, is smaller than the reconciliation tolerance of 0.00001 BTC, so
reconciliation **could not see** this omission. On a 0.05 BTC live account (8 contracts), it would have been large enough to be caught within a few days.

## §20 Demo observation (2026-10-04/12/14): offset of +2.03~2.07 s against `/time` at 00:05 UTC — cause: the MacBook's clock (confirmed 10-16)
